研究日期：2026-09-20。狀態：第一階段研究與規劃完成；已開始建立 Electron 骨架與音訊管線。模型由使用者提供，僅參考 faster-whisper 與 sherpa-onnx 的語音處理設計。

目前已完成：Electron 主程序與安全 Preload、麥克風列舉與選擇、錄音中切換輸入、RMS／peak 音量條、WebM 錄音、音檔與 TXT 保存、TXT／SRT／JSON 字幕匯出、記錄工作區、檔案匯入入口、設定工作區，以及自有模型的字幕適配器契約。待完成：串接實際模型並取得即時原文與譯文、將匯入檔案提交至模型、系統音源、WAV 匯出、浮動字幕與跨平台 Electron 實機驗收。模型接入說明見 [自有模型接入契約](MODEL_ADAPTER.md)。

## 1. 目標與範圍

以 Vurbo.ai 的使用流程與功能為參考，建立使用 Web 技術開發、由 Electron 封裝的桌面應用程式。核心流程：選擇音源 → 確認收音 → 開始錄音 → 即時原文及翻譯字幕 → 停止 → 保存音檔與逐字稿。

使用者原文的 T2S，依五項需求解讀為 STT／S2T（Speech-to-Text，語音轉文字）；TTS（Text-to-Speech，文字轉語音）列為後續口譯功能。「因檔」解讀為「音檔」。

第一個可用版本必須具備：

1. 真實麥克風收音與錄音。
2. 真實串流辨識、即時原文及翻譯字幕。
3. 音檔與逐字稿本機保存、匯出。
4. 清晰、與實際音訊同步的音量顯示條。
5. 音源列舉及切換，包括錄製中的切換與裝置拔除處理。

暫定繁體中文介面、繁體中文與英文優先；Windows 與 macOS 為目標平台。先在目前的 macOS 開發環境驗證，再以 Windows 實機驗收。瀏覽器版本共用 UI，但桌面功能以 Electron 成品為驗收對象。這些為規劃假設，尚非使用者已確認的限制。

## 3. 第一版畫面與操作

主要工作區建議：

- 頂部：會議名稱、來源語言、目標語言、辨識連線狀態。
- 收音列：音源下拉選單、重新整理、音量條、峰值、無訊號／過載提示。
- 中央：時間戳＋原文＋譯文，以相同段落上下對照；暫定字幕使用較淡樣式，定稿才寫入正式逐字稿。
- 底部：開始、暫停／繼續、停止、錄音時間、保存狀態、匯出。
- 歷史紀錄：會議列表、重新開啟、音檔回放、逐字稿匯出。

使用者捲動閱讀舊內容時暫停自動捲動，提供「回到最新」。音量條不能只靠顏色傳達狀態，需搭配刻度與文字。

第一版暫停定義為「錄音與送往辨識的音訊一起暫停」，字幕時間戳依有效錄音時間前進；另記錄牆鐘時間與暫停事件。停止後進入收尾狀態，等待最後音訊及字幕，成功寫入後才顯示「已保存」。

## 4. 技術架構建議

採 **Electron + React + TypeScript + Vite**，介面與桌面應用層使用 TypeScript；透過模型適配器串接使用者自有模型；執行位置、傳輸協定與模型端語言依使用者現有介面決定，不預設 Python 或本機推論。理由是音訊、字幕、檔案與 IPC 有大量非同步狀態，明確型別有助於維持一致性。打包工具暫採 Electron Forge；正式開工時確認相容版本並鎖定依賴。

```text
麥克風／系統音訊
       ↓
Renderer：AudioSourceManager → 共用音訊管線
       ├─ 音量分析 → UI
       ├─ PCM 分塊 → Preload → Main 寫入本機錄音
       └─ PCM 分塊 → Preload → Main → ModelAdapter → 使用者自有模型／翻譯介面
                                                      ↓
UI ← Preload ← 字幕事件正規化、排序與去重 ←───────────────┘
                  ↓
           逐字稿日誌與會議資料
```

所有分支使用同一音源管線，切換裝置時一起切換，避免「音量條動了，字幕卻在聽另一支麥克風」。錄音不可依賴辨識成功；網路失敗時仍能保存本機音訊。

| 層 | 責任 |
| --- | --- |
| Renderer | React 畫面、getUserMedia、Web Audio、AudioWorklet、音量分析 |
| Preload | 有限且具型別的 contextBridge API，不暴露任意檔案操作 |
| Main | 視窗、權限、檔案、會議狀態、服務憑證、辨識適配器 |
| Worker／Utility Process | 有需要時承接轉碼與重採樣，避免阻塞 UI／Main |
| SpeechProvider | 統一 start／pushAudio／stop 與 partial／final／revision／error 事件 |
| ModelAdapter | 對接使用者自有模型，正規化音訊請求、能力資訊與字幕回應 |
| TranslationProvider | 接收原文版本，回傳對應譯文；可映射自有模型的同一回應或獨立翻譯端點 |

Electron 設定採 contextIsolation、sandbox、關閉 nodeIntegration；IPC 驗證來源、參數及檔案邊界。[Electron 安全指引](https://www.electronjs.org/docs/latest/tutorial/security)

若未來部署獨立網站，需補瀏覽器檔案保存適配器及服務端 API，不能假設 Electron 的檔案／憑證介面直接適用。

## 5. 音訊與音源規格

### 麥克風與切換

使用 getUserMedia 取得授權後列出可用輸入，以 deviceId 指定裝置；監聽 devicechange、track ended，重新啟動後檢查原裝置是否仍存在。實作前以 [MDN getUserMedia](https://developer.mozilla.org/en-US/docs/Web/API/MediaDevices/getUserMedia) 與目標 Electron 版本核對限制。

錄音中切換流程：要求新裝置 → 確認有效訊號管線 → 記錄切換事件 → 接入共用音訊管線 → 結束舊軌道。若平台不能同時開啟兩個輸入，使用可見的短暫暫停流程；不能承諾完全無縫。失敗時保留舊來源；舊來源已失效時顯示中斷，讓使用者選擇替代裝置，不默默切換到其他麥克風。

字幕及錄音共用單調遞增的 session 時間軸。若切換需要重啟辨識串流，保存 streamId 與起始 offset，避免字幕時間從零開始、重複或錯位。切換空白期採插入等長靜音並記錄缺口，確保音檔與字幕對齊。

### 音量條

從 PCM 計算 RMS 與 peak，使用 dBFS 刻度（不是環境聲壓 dB SPL）。建議顯示 -60 至 0 dBFS，每秒刷新 20–30 次，約 1 秒 peak hold；加入平滑讓畫面穩定。初始過載提示可用 peak 接近 -1 dBFS 並持續一段時間，後續以實測調整。低電平提示只代表訊號弱，不等同麥克風故障。

驗證用數位測試訊號檢查振幅加倍約增加 6.02 dB；以 RMS 計算時正弦波需區分峰值與 RMS，不混用標準。畫面需可辨識靜音、收音中、訊號偏低與過載。

### 系統音訊

系統播放聲音不是一般麥克風 deviceId；使用 Electron desktopCapturer／getDisplayMedia 的平台能力，另測 Windows loopback 與 macOS 權限。macOS 14.2+ 的音訊擷取有 NSAudioCaptureUsageDescription 等要求；開發模式與打包成品都需驗證。部分權限錯誤可能產生沒有聲音的串流，必須檢查實際樣本。[Electron desktopCapturer](https://www.electronjs.org/docs/latest/api/desktop-capturer)

第一個麥克風 MVP 支援一個選定輸入。系統音訊及「麥克風＋系統音」混音安排後續里程碑；若使用者首版就要錄線上會議，該里程碑需提升為首版必要條件。

## 6. 即時辨識與翻譯

**模型由使用者提供。** 本 repo 負責音訊處理、模型介面適配、字幕與檔案流程；faster-whisper 與 sherpa-onnx 僅作技術參考，不列入執行依賴、不下載其預訓練模型、不預設雙引擎或 Python 程序。詳見 [技術參考與自有模型整合規格](OPEN_SOURCE_BACKENDS.zh-TW.md)。

| 模組 | 本專案負責的功能 |
| --- | --- |
| AudioPipeline | 音訊分塊、按模型需求重採樣／聲道轉換、時間軸與有上限的緩衝 |
| SpeechSegmenter | 按能力選擇模型端點事件或應用端切段；保留句首句尾緩衝 |
| ModelAdapter | 串接自有模型，支援串流或片段請求，統一 partial／final／error |
| TranscriptAssembler | 更新暫定字幕、段落排序、重疊去重、版本與時間戳映射 |
| TranslationAdapter | 接收同一模型或獨立端點的譯文，與原文版本綁定 |

原生串流模型直接處理其 partial／final；只有片段輸入能力時，另外驗證切段或滑窗策略，不把整句回傳包裝成逐字串流。採樣率、VAD、時間戳與翻譯能力由實際模型介面決定。應用端 VAD 若需要模型，需另行確定來源，不因參考 repo 而默認引入其依賴。

定稿以 segmentId、revision 去重及更新；遲到的舊譯文不得覆蓋新版本。翻譯失敗保留原文。模型連線或運算失敗時繼續本機錄音，標記未辨識區間；重連是否能補送依服務能力決定，不默默重送造成重複字幕。離線可用性取決於自有模型部署位置。

若模型需要認證，憑證由 Main 或既有後端管理，不寫入 Renderer、Git 或打包程式碼。只傳送必要資料到使用者設定的模型端點；不自行選用第三方雲端供應商。翻譯是首版必要功能，若自有模型不提供譯文，需對接使用者指定的翻譯介面。

## 7. 本機保存與匯出

第一版以 PCM16 WAV 為可靠的共通音檔格式，透過 AudioWorklet 分塊傳送並增量寫入；實際採樣率與聲道記錄在檔頭，辨識分支另依自有模型輸入規格重採樣。不能只修改採樣率標籤。音訊 buffer 必須有上限及背壓，不將整場錄音累積在記憶體。

例如單聲道 48 kHz／16-bit 約 346 MB／小時；以此估算磁碟需求。後續壓縮格式可降低容量。MediaRecorder 可作壓縮方案，但需檢查 MIME 支援、容器收尾與恢復能力，不能直接把 WebM 改副檔名當 MP3。[MDN MediaRecorder](https://developer.mozilla.org/en-US/docs/Web/API/MediaRecorder)

```text
sessions/<sessionId>/
  session.json          # 語言、時間、狀態、音源及採樣格式
  audio.wav.part        # 錄製中；完成後修正檔頭並改名 audio.wav
  transcript.jsonl      # 增量事件、定稿、翻譯更新
  events.jsonl          # 暫停、切換、辨識斷線、錄音缺口
```

字幕資料至少包含 id、revision、startMs、endMs、sourceText、translatedText、sourceLanguage、targetLanguage、streamId、狀態。保存失敗不能顯示成功；磁碟不足停止錄音並保留已寫資料。重新啟動檢查未完成會議，以已落盤 PCM 長度修復 WAV 檔頭，忽略／截斷最後不完整日誌行。

匯出：WAV、UTF-8 TXT（原文／譯文／雙語）、SRT（含正確起訖時間）、JSON（完整結構）。TXT、SRT 必須從同一份定稿資料產生。使用者選擇保存位置；覆寫走明確的系統提示。停止時先停止新音訊、排空佇列、等待辨識收尾或超時標記、完成音檔，再回報保存結果。

## 9. 驗收計劃

| 使用者需求 | 可檢查的完成標準 |
| --- | --- |
| 可以收音 | 內建及 USB 麥克風各錄 10 分鐘，播放可聽見完整內容；拒絕權限時顯示可操作訊息 |
| 即時字幕與翻譯 | 繁中→英文、英文→繁中各以固定測試素材及真人輸入測試；字幕持續更新、定稿不重複、翻譯與原文段落相符 |
| 保存音檔與逐字稿 | 關閉並重啟後能開啟會議；WAV 可播放、TXT 中文正常、SRT 可匯入播放器且時間對齊 |
| 清晰音量條 | 靜音、一般說話、大聲輸入有不同狀態；數位振幅測試正確；切換後反映新音源 |
| 切換音源 | A→B→A 多次切換後 UI、錄音、辨識一致；拔除裝置有提示；無效裝置不導致程式崩潰 |

延遲為工程目標而非 Vurbo.ai 實測或本系統保證：在記錄網路與設備條件下，取至少 30 句，量測首個有效語音樣本到首個 partial，以及句末到 final 譯文；初始目標 p95 分別 ≤2 秒、≤4 秒。若未達標，分別量測收音、切段、傳輸、模型推論與畫面更新，再調整應用處理及與模型端協作，不能用假字幕通過驗收。

辨識品質另以至少 50 句人工標註繁中／英文素材檢查，包含專有名詞、數字、日期、安靜與背景噪音。PoC 交付 CER／WER、數字錯誤、漏句、翻譯錯意案例；正式門檻依實際場景訂定，不能用單一句子宣稱準確率。

穩定性需測：60 分鐘連續錄製、網路斷開及重連、金鑰錯誤、服務限流、磁碟不足、強制關閉後恢復、系統休眠／喚醒。檢查記憶體不隨錄音長度持續累積、時間戳不倒退；崩潰恢復僅保證已落盤部分，實測記錄最大損失時間。自動化聚焦段落去重、時間軸、音量算法與匯出格式，硬體和權限採實機驗收。

## 10. 開工前需收斂的選擇
