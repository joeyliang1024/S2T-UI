# 文件撰寫規範

先問文件回答哪個問題，再決定放置位置。入口只做導覽；同一契約或操作流程維持一份權威來源。

## 文件類型

| 內容 | 放置位置 | 必備內容 |
| --- | --- | --- |
| 使用／部署／復原步驟 | `docs/guide/<TOPIC>.zh-TW.md` | 適用版本、前提、步驟、預期結果、失敗處理 |
| API／資料／架構契約 | `docs/reference/<TOPIC>.zh-TW.md` | 邊界、不變條件、輸入輸出、錯誤、相容性 |
| 可行性與方案比較 | `docs/research/<TOPIC>.zh-TW.md` | 問題、來源、事實／推論、取捨、未驗證事項 |
| 審查與執行結果 | `docs/reports/<TOPIC>_YYYY-MM-DD.zh-TW.md` | 日期、commit、範圍、方法、證據、限制 |
| 可提交結果 | `docs/reports/` 與 `docs/en/` | 精簡結論、環境、驗收限制及重現指南；原始實驗僅在本機忽略目錄 |
| 跨主題導覽與開發規範 | `docs/wiki/<Page-Name>.md` | 可讀的摘要、單一來源連結、維護方式 |

既有英文檔名不因新規範強制改名。新檔名用穩定英文主題，Wiki 用 `Title-Case-With-Hyphens.md`；主標題可用繁中。不要用 `final`、`new`、`v2-final` 當檔名。

## 寫作要求

開頭先寫用途、適用範圍及狀態。明確區分「已實作、已用 mock 驗證、已做真實環境驗收、仍為提案」。會過期的數字附日期／commit／環境；不可把 CPU 量測套成 H100／H200 結果。

repo 內優先使用相對連結；Wiki 指向程式或 repo 文件時使用完整 GitHub URL 並標明 ref。跨分支路徑先確認存在。程式搬移、指令／預設值、環境變數或錯誤語意改動，應在同一 PR 更新相應文件與索引。

命令說明工作目錄、前提、會修改的資料及成功標準。使用 `<namespace>`／`<fixture.wav>` 等明確占位符；不要放個人絕對路徑、真實 API key、Secret、cookies、連線密碼或完整帳號資料。破壞性操作不得作為不加說明的預設指令。

## 通用範本

````markdown
# <主題>

狀態：<現行／提案／實驗紀錄>
適用版本：<branch／commit／release>
更新日期：<YYYY-MM-DD>

## 用途與範圍
<讀者要完成什麼，哪些條件適用>

## 前提與操作
<環境、資料、指令或契約>

## 預期結果與證據
<執行內容、結果、指標與可重現入口；未執行請明寫>

## 限制與失敗處理
<限制、回復方式、未驗證事項>

## 相關來源
<repo 文件與直接支持結論的官方來源>
````

repo 的 `docs/templates/` 可提供分類範本。新增／搬移文件後更新 `docs/README.md`；可提交結果同步更新 `docs/reports/README.md` 與中英文重現指南；`experiment/` 除根入口外不追蹤；Wiki 新頁更新 `_Sidebar.md` 與 Home。

已完成開發不留在 enhancement 當歷史；驗收清單留在驗收手冊，報告與 experiment 保留方法和證據。舊文件若被替代，留下導向或更新引用後再刪，避免斷鏈。
