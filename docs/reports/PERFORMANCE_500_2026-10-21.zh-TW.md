# 500 人效能修正與驗證

> 歷史／研究文件：以下數據、路徑與命令僅代表記錄版本，不是現行操作入口。最新操作與驗收請以 [文件入口](../README.md)、[目前結果](VALIDATION_2026-10-26.zh-TW.md) 及 [重現指南](../guide/REPRODUCE.zh-TW.md) 為準。


驗收基準：2 個 Gateway Pod；500 名不同帳號，持續 600 秒；ASR 與翻譯模型各固定 500ms。每人每 2 秒送 2 秒 16kHz PCM 音訊，同時保存錄音分段，每 10 秒保存草稿。ASR E2E 為最後語音至原文 paint；翻譯 E2E 為同一語音終點至譯文 paint，包含 ASR。

延遲驗收依最新要求採 P90：ASR E2E P90 <3 秒，包含 ASR 的翻譯 E2E P90 <3 秒。HTTP 成功率、丟棄數獨立檢查；P95/P99/max 與 ≥3 秒數保留診斷，不作延遲主門檻。

已完成兩輪 500 人 10 分鐘實測，仍未通過；修正版的 500 人完整驗證仍待重跑。後續 100 人完整測試已通過 P90 與成功率，詳見 [100 人修正總報告](PERFORMANCE_100_2026-10-22.zh-TW.md)。下列數字不是驗收通過的宣告。

## 已重現的程式問題

- 原帳號刪除保護把 PG session 持有到模型或上傳結束，形成低併發上限。改為固定共用 advisory-lock sessions、批次入場／釋放；推論的耐久 request leases 只在短 PG 交易中檢查帳號狀態。
- 逐筆 durable request lease、認證及錄音 metadata 造成大量 PG 往返。合併有限大小的批次，保留 fsync、租約 owner、指紋衝突與刪除隔離。
- 自適應容量對每筆失敗與等待逾時反覆減半，導致可用容量降到 1 並持續延長 cooldown。改成一次故障期只降一次，入場等待逾時不縮減後端容量，PG 保留最低處理容量。
- Sentinel 客戶端並行 command proxy 在 500 次 PING 測試中，3 秒內只完成 4 次；直接 Redis 約 6ms 完成 500 次。初版 `use()` 每命令重建介面仍有熱點；CPU profile 證實後改為一次取得固定 4 個公開 `acquire()` 租借物件，管線化重用，並把滑動視窗限流合併為原子批次。修正後真實 Sentinel 的 500 次檢查約 96ms，500 個各 500ms 的操作約 540ms 完成，峰值併發 500，無剩餘等待。
- 重複 DNS 查詢讓大量 socket 建立排隊。模型 HTTP、MinIO、Sentinel 與壓測端共用 5 秒、最多 128 主機的查詢合併快取，保留地址家族順序及過期後重新解析。
- readiness 逐筆 schema 查詢與業務共用 PG 佇列，獨立檢查串行的最壞期限也接近 K8s 探針期限。改用最多 1 條專用 PG 連線、並行依賴檢查與 Server-Timing。metrics 的 backlog 查詢改為有新鮮度指標的背景快照，PG 卡住時仍可抓取其他指標。
- API 回應串流未消費就取消會留下 permit；已加入取消釋放。前端 ASR／匯入支援有界並行，提交與 checkpoint 維持音訊順序。
- 原 API 錯誤計數漏算中斷。加入早期 HTTP 狀態／斷線計數，壓測另驗證回應內容、記錄逾時與丟棄。
- CPU profile 找到 JWT 每次重新解析金鑰、模型 SDK 每次重建與 prompt 每次重新初始化檔案。改成共用 HMAC KeyObject、有界 64 個 SDK client，及檔案版本快取；每次仍查詢最新帳號／撤銷狀態，prompt 修改下一次讀取即可生效。
- PG 清理過期 request 的整表 DELETE 在 20 萬筆資料時反覆 statement timeout。改成主鍵游標每次最多掃 1,024 筆，每秒一頁，`SKIP LOCKED` 避開活躍請求；只刪除過期 request，不改 schema。PG 容量判斷另避免把整個交易的 JavaScript 時間誤當短 SQL 超載。
- 模型 HTTP 的 2 秒 keepalive 與音訊 2 秒週期重疊，MinIO 也在活躍容量增加後仍僅保留 16 個 idle sockets。調整重用窗口；MinIO 的空閒連線跟隨有界容量，control pool 閒置 floor 16；已測 worker floor 16，提交原始碼後續改為 64，未計入既有測試成效。
- MinIO 啟動時短暫拒絕連線會使 `ready` 永久失敗。加入最多 30 秒的短暫故障重試，403 等權限錯誤仍立即失敗。
- 成功 HTTP 的逐筆 access log 移至 debug；錯誤與每次請求的 KPI 計數保留。測試原本採 warn，因此不能把這項調整當成壓測改善證據。

## 第一輪完整 600 秒結果（失敗）

2026-10-21 14:53:41–15:03:41 UTC，固定 2 Pod、四端各 125 名不同用戶，模型各 500ms。提供 150,000 段，丟棄 47,254 段，實際完成 102,746 條 ASR→翻譯鏈路。送出的 322,354 次 HTTP 有 781 次失敗，HTTP 成功率 99.758%；以全部提供音訊計算的鏈路成功率只有 68.497%。

| 指標 | P95 | P99 | 最大值 | ≥3 秒數 |
| --- | ---: | ---: | ---: | ---: |
| ASR HTTP | 3.224s | 4.105s | 5.363s | 8,398 |
| 翻譯 HTTP | 2.712s | 3.404s | 6.757s | 2,749 |
| ASR→翻譯 HTTP | 5.632s | 6.680s | 9.554s | 76,126 |
| 錄音上傳 | 4.578s | 6.343s | 11.689s | 23,634 |

MinIO 在原 768Mi 上限發生 OOM，產生連線拒絕／重設與 socket timeout；另有 10 次錄音 metadata admission timeout。下一輪改為 1536Mi，資料磁碟保留。兩個 Gateway 沒有重啟，但 CPU 接近各一個核心，事件迴圈 P99 約 0.2 秒。

瀏覽器與負載起跑偏差 13ms，但中途 kubectl port-forward 因 socat Broken pipe 終止，後半段探針失效，因此該 E2E 報告不能當作完整驗收。下一輪改成僅綁本機的 Colima SSH 到 Gateway Service 通道。

Prometheus 原 512Mi 發生 OOM，已保留 PVC，先改為 1Gi，後續提高至 1536Mi；累積開發測試產生約 41 萬 time series。低基數 runtime 指標每 5 秒抓取，用戶統計每 15 秒抓取，並移除非模型路徑永遠為零的 token／audio series。原 `/metrics` 相容，原 dashboard 標籤維持 `job=s2t`。Colima 節點 IP 改變造成服務發現白名單過期，亦已修復；第一輪前幾分鐘的 Gateway Grafana 指標有缺口，以產生端原始紀錄補足 HTTP 統計。

## 第二輪完整 600 秒與 P90 重算（仍未通過）

2026-10-21 15:10:06.98–15:20:06.98 UTC，500 用戶、固定 2 Pod。提供 150,000 段，丟棄 61,768 段；277,443 次 HTTP 中 17 次失敗，HTTP 成功率 99.99387%，offered 鏈路成功率 58.8173%。MinIO 提高至 1536Mi 後沒有再次 OOM，但整體吞吐及翻譯延遲仍不足。

同步瀏覽器與負載起跑差 9ms，250 組原文／譯文，無瀏覽器或傳輸錯誤。依保留的原始樣本，以 nearest-rank 重算精確 P90：

| 瀏覽器指標 | P90 | 3 秒延遲門檻 |
| --- | ---: | --- |
| ASR E2E | 2.447s | 通過 |
| 包含 ASR 的翻譯 E2E | 4.150s | 未通過 |
| t5 network | 0.145s | 診斷用 |
| t7 network | 0.099s | 診斷用 |

這是一個瀏覽器在 500 人負載下的抽樣，不代表 500 個瀏覽器。舊 HTTP 摘要沒有完整原始樣本，因此不補造其 P90。重算結果另存 `browser-p90-recalculation.json`，舊結果不覆寫。

後續修正已加入草稿 checkpoint 批次、Redis 推論容量非同步釋放，以及 MinIO 小物件背景 worker。最新 60 秒診斷提供 15,000 段、丟棄 512 段，HTTP 無錯誤；同輪瀏覽器 ASR E2E P90 2.190s、翻譯 E2E P90 5.128s，仍未達標，且不能替代完整 10 分鐘驗收。

## 已完成的回歸

- unit 86/86，HTTP 17/17。
- TypeScript、架構檢查、Web build 通過。
- 真實 PG：500 次 metadata 更新無遺失、批次錯誤隔離、request cache／衝突、過期 lease 替換、舊 owner 拒絕、pool max=1、斷線重連、帳號刪除後不重建資料。
- 真實 pg driver：黑洞 query timeout、淘汰死連線、重新連線、不殘留等待項目。
- DNS：500 次同主機只查一次、有限快取、TTL 與故障恢復；HTTP 串流取消後 permit 釋放。

## 連線與資料安全

每 Pod 的測試 PG 預算為 queries 12 + fence 5 + health 1 = 18，2 Pod 最多 36；測試 PostgreSQL 上限 64，另留監控與測試工具空間。fence 包含最多 4 個共用 session 與 1 個刪除專用 session。Redis master pool 固定有界為 4，Redis 命令由合併批次控制，不隨用戶數無限增加。

沒有關閉 PG fsync、清空 PG／Redis 或重建現有帳號資料。故障驗證只終止測試自己建立的 backend。MinIO 測試資料切換至既有 40GB VM 資料磁碟前先複製保留，避免 10 分鐘新增約 9.6GB 錄音耗盡根磁碟。

## 驗收方法與限制

四個 K8s 產生端各 125 用戶，同步開始；分位數以四端實際樣本合併計算，不平均各端分位數。報告包含各端點成功率、HTTP 狀態、傳輸錯誤、丟棄、P50/P90/P95/P99/max、≥3 秒比例、每分鐘結果，以及產生端事件迴圈延遲。舊 HTTP 摘要未保留 P90 或完整原始樣本時，不從 P95 反推 P90；保留原始瀏覽器樣本者另重算並標明來源。

Chromium 抽樣探針走正式 VAD、ASR adapter、翻譯 queue 與雙 RAF 字幕 paint，並上報 t5/t7；此抽樣不能宣稱等同 500 個實體瀏覽器。合成 PCM 不包含實體麥克風、Silero 模型與外部 WAN。完整 HTTP 鏈路與瀏覽器 E2E 分開報告，任何超過 3 秒的樣本均保留。

實際結果檔位於 `experiment/evaluation-reports/k8s-performance/`；開發期失敗與不完整報告明確標記 `development-*`，不能充當最終結果。
