# 五分鐘即時字幕比較實驗

日期：2026-10-04（Asia/Taipei）。素材：指定「財富階梯 Wealth Ladder｜啾啾鞋」影片的 00:00–05:00。

## 先看結論

- **優先建議：將字幕顯示分組與 ASR／翻譯片段分開。** 正常檔同一批文字由 200 列降為 34 列；短列（少於 8 個正規化字元）由 40% 降為 0%。沒有額外模型請求，不需要等待更多音訊。這是閱讀與版面的改善，並未提高辨識正確率，也不保證每一列就是完整語義句子。
- **300 ms 重疊是目前較值得驗證的 ASR 修正候選。** 正常檔草稿差異率 12.44%→8.43%，塊起點到結果到達 P95 2175→2003 ms。重跑值 8.43%。是否維持每一檔速度，見下面驗收表。
- 600 ms 重疊的初輪全文差異略低，但多用音訊、延遲餘裕較小；180 字上下文與本輪術語表沒有支持全面替換目前預設。術語表能改正與影片名稱一致的姓名，不能據此推論全文更準。
- LocalAgreement 需要另看預覽修正與固定前綴，不能把較晚的整塊定稿時間當成首批預覽時間。此輪原型是一般 HTTP 上的字元前綴一致策略，**不是 SimulStreaming，也不是有詞級對齊的原作者實現**。

**準確度限制：參考 TSV 是未校對的機器草稿。沒有完成聽音人工核對，因此本報告不提供正式 CER，也不宣稱已證明真實正確率提升。** 原文／譯文保存與延遲可實測；「換句是否自然」仍須聽音核對回放案例。

**關鍵反例：** 在 90–108 秒的「淨資產／收入直接中斷」附近，重疊也產生了「羞辱」「種段／種族」等與草稿不一致的內容。**目前不建議全域預設開啟音訊重疊**；它是需人工核對與可回退的候選，不是已驗收的準確度修正。見 [核對案例.md](../../experiment/captions/comparison-2026-10-04/核對案例.md)。

**三檔結論：** 300 ms 重疊在快檔與正常檔配對重跑未通過速度門檻；慢檔通過（草稿差異率 8.49%→4.84%，塊級 P95 增加 69 ms）。只有慢檔可列為人工核對後的小範圍候選，不能將其結果套到快／正常檔。

「草稿差異率」：正規化後全文 Levenshtein 字元距離／參考字元數；五分鐘共有 18 個參考區間、1672 個正規化字元。區間平均長度約 17 秒，並非人工語義句子；每句拆段數不能由它直接得出。

「區間起點→首批」是第一筆時間範圍覆蓋該參考區間的文字到達時間，樣本只有 18 個；不是逐字實際發聲延遲。「塊起點→收到字幕」包含切段等待與推論，樣本較多；另保存塊結束到結果、ASR 耗時與排隊時間。兩者都排除實際 React／DOM 繪製。

### 速度驗收

原定門檻：相同檔位的 P95 增幅不超過 100 ms 或基準的 5%，取較大者。保留原先首批指標，另列塊級指標，避免只挑有利數字。

60 秒評分只含完整落在測試範圍內的兩個參考區間，主要涵蓋前 43.6 秒；邊界音訊塊可能帶入鄰近文字。這些分數僅供初篩，正式建議以五分鐘結果為主。LocalAgreement 的塊級欄位使用「最近輸入步長起點→預覽更新」，不是整塊定稿時間；沒有測翻譯。

### LocalAgreement 與端點能力

最終採用受限文字邊界對齊原型，固定前綴被改寫次數 0，模型新假設與已固定前綴不一致 6 次，暫停更新 0 次。可變尾端有 5 次修正；預覽更新 P95 2953 ms。各視窗第一段固定前綴到達 P95 4261 ms，這不是逐字穩定時間，不能當作詞級延遲。

其草稿差異率較低，但預覽更新的塊級代理指標比正常檔慢，未進入五分鐘正式比較。先前兩個除錯原型保留在實驗套件中，因固定前綴與接續處理尚不完整，未納入正式比較表。

- 模型拒絕詞級時間戳請求：HTTP 400，Currently only support response_format `text` or `json`。OpenAPI 宣告的欄位不代表此模型實際支援。
- SSE 文字輸出確實可用：四秒探測第一個 body chunk 371 ms，完整回應 785 ms。**只有四秒能力探測，沒有五分鐘 SSE 效能驗證**；可作下一輪候選，不能套用本輪結果來保證各檔速度。它仍須先上傳整段音訊，不是 SimulStreaming 或持續音訊輸入。

## 實作與隔離

- 讀取專案目前的 EnergyVad、OpenAiChunkedModelAdapter、upsertLiveCaption 與 TranslationQueue；esbuild 在記憶體打包，不重建或修改專案。48 kHz 單聲道、20 ms 一批，以單調時鐘按真實節奏輸入。
- 固定來源繁體中文、目標英文；仿 Electron 的 system／user 翻譯 transport，沿用正式翻譯佇列、220 ms 排程與 2 筆並行。沒有驗證使用者目前 Web／Electron 設置是否完全相同，也沒有走正式 Web gateway 的前處理與限流。
- 300／600 ms 只加在強制切段音訊的左端，不改變正常片段結束時間；文本去重限定已知重疊邊界，採繁簡／標點正規化後的前綴與上一段後綴匹配，必要時最多容忍一個字元差異。沒有詞級時間對齊，仍有重複、漏字與誤刪風險。
- 顯示合句是純投影：保留每個原始 ID、原文與譯文。間隔達 600 ms、自然 VAD 句界、講者變更或 10 秒上限時分組；短片段優先接續，達約 70 字或足夠長的終止標點再換列。參數只在此素材測試，不是通用最佳值。
- 分組 CPU 的 400 次取樣 P95 為 0.536 ms；不包含 React 繪製。
- 正規化：NFKC、小寫、macOS ICU Hant-Hans 字元表、中文／阿拉伯數字轉換、移除標點與空白；不做同義詞修正。數字單位和專有名詞仍應另看案例，不能只看正規化總分。

## 保留與失敗檢查

獨立控制測試已驗證：翻譯進行中不合併原始所有權、完成譯文不消失、顯示分組保留全部原文、自然句界／大停頓分開、尾段排空、投影不修改原資料。每輪原始結果還保留丟段、空回應、排隊與尾段時間，供核查。

英文目標的正常檔基準有 21／200 筆譯文含漢字；這是語言粗檢，不代表 21 筆全部是錯譯，但回放中可見部分中文或其他語言輸出。完成數表示佇列成功收到非空文字，不表示翻譯品質已驗收。合句只保留拼接現有譯文，尚未解決譯文語義斷裂。

## 建議怎麼修正（本次未套用）

1. **顯示層先改。** 在 live-caption／字幕視圖加入帶原始片段 ID 的顯示分組；翻譯與保存繼續依原始片段處理。讓文字收到即顯示、繼續接句，避免正在翻譯就必須新開一列；不要恢復會清空已有譯文的資料合併。
2. **ASR 重疊保留為可回退的候選。** 若人工核對支持、且相應檔位速度通過，再在 model-adapter 的強制切段保留 300 ms 左側上下文；控制去重並保留完整錄音，先處理因邊界截斷而漏掉的字。不要一開始全域啓用 600 ms，也不要在自然句界重復音訊。
3. **術語小範圍使用。** 沿用現有 prompt 接口，提供用戶確認的姓名、書名／產品名；避免把本輪理財術語表變成所有錄音的默認。擴大上下文的方案目前不建議採用。
4. **LocalAgreement／SimulStreaming 另立模型端驗證。** 此輪客戶端原型若需要固定前綴衝突時暫停更新，會增加穩定文字等待。真正的注意力導向解碼需要模型端支援；SSE 輸出流並不等於持續輸入音訊的串流辨識。

## 後續已批准的顯示修正（2026-10-04）

使用者批准第一輪實作後，新增 `groupLiveCaptions` 純顯示投影，套用於即時字幕主視圖與 Web 字幕浮窗。主視圖可展開原始片段，編輯、講者標記、手動翻譯與失敗重試仍以原始 ID 操作；翻譯到達時重算顯示分組，不等待音訊或額外呼叫模型。

停止在 `upsertLiveCaption` 中以新 ID 合併未翻譯片段，保留原始記錄供翻譯與保存。ASR、VAD、重疊、模型設定、翻譯佇列的時間與並行設定均未修改。移除資料合併後，在原先會合併未翻譯片段的情境，翻譯請求數可能改變；未宣稱所有策略的請求量完全相同。
