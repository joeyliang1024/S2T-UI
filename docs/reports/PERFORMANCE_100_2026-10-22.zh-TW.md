# 100 人／2 Pod 效能實測（2026-10-22）

> 歷史／研究文件：以下數據、路徑與命令僅代表記錄版本，不是現行操作入口。最新操作與驗收請以 [文件入口](../README.md)、[目前結果](VALIDATION_2026-10-26.zh-TW.md) 及 [重現指南](../guide/REPRODUCE.zh-TW.md) 為準。

後續已完成「100 名即時用戶＋32 個背景模型執行者」的完整 600 秒驗證，結果與監控修正見 [即時優先混合驗證報告](REALTIME_PRIORITY_2026-10-22.zh-TW.md)。本文保留原先單純 100 人測試數字。

本輪 P90 與 HTTP 成功率驗證通過。測試時間為台北時間 2026-10-22 00:08:49–00:18:49，固定 2 個 Gateway Pod，100 個不同帳號，持續 600 秒；ASR 與翻譯模型各等待 500ms。每人每 2 秒送 2 秒 PCM 並保存錄音分段，每 10 秒保存草稿，四個產生端各 25 人同步發送。

本輪沿用上一輪 Gateway 映像與連線池設定，沒有為 100 人修改應用程式設定、重建 PG 或清除既有資料。測試工具加入可設定總人數，原始 HTTP 樣本另存 gzip，P90 由四端完整樣本合併計算。Gateway 使用 Node 選項 `--experimental-async-context-frame --max-semi-space-size=64`，每 Pod PG query 上限 12，另有 fence／health 預算；詳細映像 ID 見 verdict 檔。

## 之前的問題與此次修正

| 原本問題及影響 | 此次修正 | 驗證與限制 |
| --- | --- | --- |
| PG 帳號保護長時間持有 session；模型或上傳變慢時，連線跟著被占住 | 共用有界 fence sessions；request lease／錄音 metadata／checkpoint 使用短交易與有界批次，模型推論不持有專用 PG session | 真實 PG 驗證 500 次 metadata／checkpoint 更新、pool max=1、刪除競態；此輪 100 人沒有耗盡 |
| PG 斷線後應用程式可能繼續等待，缺少連線健康與查詢期限 | 加入 TCP keepalive、connect／query／statement／lock／idle transaction timeout；接收 pool error 並淘汰死連線；readiness 獨立 1 條連線 | 驗證黑洞 query timeout、終止測試自身 backend 後重連；沒有關閉 fsync 或清空資料 |
| 自適應容量在同一故障期間反覆減半，排隊逾時又觸發降容，造成忽快忽慢 | 有界 admission、緩慢加法擴容、故障快速減半及 cooldown；單純等候逾時不判成後端故障，PG 保留最低容量 | 回歸覆蓋慢升快降、等待清理與故障恢復；各服務維持硬上限，不隨用戶數無限加連線 |
| Sentinel command proxy 並行取得 lease 的競態與每命令重建介面，讓 500 次 PING 僅少數完成 | 固定重用 4 個公開 acquire lease；滑動限流及模型入場使用原子 Lua 有界批次；推論完成後非同步釋放容量 | 真實 Sentinel 診斷達峰值 500 並行；容量釋放前仍算占用，避免超賣。尚未完成真實 Sentinel 切主驗證 |
| 前端 ASR／匯入逐筆等待，無法供應模型已有的並行容量 | ASR 與匯入使用最多 4 個並行工作；結果依音訊順序提交，checkpoint 只前進至連續完成的位置；取消會中止在途匯入請求 | 驗證有界並行、順序與錯誤處理。單人窗口是 4，跨用戶可同時推論，不是全系統一次一筆 |
| 重複 DNS、SDK client 建立、JWT 金鑰解析與 prompt 檔案初始化占用 CPU，並增加 t5／t7 等待 | 共用有界 DNS 快取／查詢合併、每角色 HTTP Agent、最多 64 個 SDK client、HMAC KeyObject 及檔案版本快取；實際串流結束／取消才釋放 permit | 分路徑 500 次診斷及 DNS／HTTP 回歸；保留每次帳號／撤銷狀態檢查，prompt 修改可生效 |
| 錄音逐筆 S3 簽名／序列化占主執行緒；長錄音 metadata 反覆全量掃描 | 小 Buffer PUT 交給每 Pod 一個有界 worker，control 16 + data 112 共 128 sockets，待處理 payload 上限 64MiB；維護錄音 end-sample 高水位 | 實際 SDK 並行寫入、caller Buffer 不被 detach、durable ACK 與 out-of-order overlap 回歸；上傳長尾仍存在 |
| 過期 request 整表 DELETE 在資料成長後反覆 statement timeout | 主鍵游標每次最多掃 1,024 筆，以 SKIP LOCKED 避開活躍列，只刪已過期 request | 真實 PG 暫存 shadow table 驗證分頁清理與保留有效／其他記錄；未新增 schema migration，清理延遲仍需改善 |
| HTTP 中斷未完整計入成功率；metrics 查詢會被 PG 卡住，監控本身又有高基數與 OOM | 提前記錄狀態／斷線；驗證成功回應內容，另記 offered／dropped；背景 backlog 快照、runtime／user scrape 分流，新增池、佇列、P90、t5／t7 dashboard | 保留原 dashboard；此輪以四端原始樣本精確合併 P90，不平均分位數。監控與模型外延遲均保存 |

MinIO 在先前 500 人測試曾因 768MiB 上限 OOM，測試環境提高至 1536MiB；Prometheus 保留既有 PVC 並提高至 1536MiB。錄音測試資料先複製再遷移至 VM 資料磁碟，沒有刪除既有資料。瀏覽器通道由容易因取消請求中斷的 kubectl port-forward 改為本機 SSH 到 Gateway Service。

### PG 與外接服務預算

每 Pod：PG queries 12 + fence 最多 5 + health 1 = 最多 18，2 Pod 最多 36；測試 PG max_connections=64，保留管理及監控餘裕。Redis master command lease 每 Pod 固定 4。模型 HTTP 每角色硬上限 512、初始 admission 256；這是容量上限，socket 按需要建立。Redis／MinIO／HTTP 等候皆有數量或時間限制。

PG 預設期限：connect 3s、query 6s、statement 5s、lock 3s、idle transaction 10s；keepalive delay 1s、閒置 client 5s。這些是資源／故障期限，不等同字幕延遲 SLA。一般連線錯誤不會主動終止其他帳號的 backend；故障測試只終止自己建立的 backend。沒有危險 schema 操作、關閉耐久性、全庫刪除或 Redis FLUSH。

### 本次原始碼與已測映像的差異

100 人測試實際映像為 `sha256:827a3f7eb8f94bc2bc2d0447f83d28a334f5c617e82957885e10489e17734ebb`。本次提交另含 host PSI 背景指標與 MinIO worker 閒置容量 floor 64 的後續調整；這兩項尚未部署於本輪映像，因此不宣稱它們帶來上述測試結果。提交前另執行完整回歸；正式採用提交版本前仍應重新建置及部署驗證。

## 長尾及 Grafana 觀察

P90 通過仍有長尾：瀏覽器原文 2／250 組、譯文 9／250 組超過 3 秒。ASR E2E P99 2.364s、最大 3.572s；翻譯 E2E P99 4.165s、最大 4.771s。全負載 HTTP 鏈路有 1,474／30,000 段超過 3 秒，錄音上傳最大 6.516s，均未從樣本移除。

已保存整輪 Grafana query_range；以下為抓取到的數值，5 秒 gauge 抽樣可能漏過短峰：

- PG query waiting 每 Pod 最高 1／2，fence 與 health waiting 均為 0；沒有持續累積到耗盡。Redis waitingCapacity 最高 35，pendingCommands 最高 8；MinIO waiting 最高 22。測試完成後產生端已停止。
- Gateway event-loop P99 抓取值最高約 291ms；單 Pod 的 30 秒 CPU rate 最高約 0.76 核。共享 VM 執行延遲仍值得改善。
- 儲存延遲仍有尖峰：每分鐘 histogram P95 估計最高，過期 request 清理約 2.575s、錄音 metadata 約 1.139s、MinIO PUT 約 1.628s。這些是診斷區間估計，不是整輪精確分位數，也未證明單項與字幕尖峰的因果關係。
- MinIO working set 抓取最高約 1465.5MiB，接近 1536MiB 上限，這輪沒有重啟；記憶體餘裕仍有限。舊映像尚無新增 host PSI gauge，因此報告中的 host_pressure／host_load 缺值不當成零。

此次只證明上述環境下 100 人、10 分鐘的 P90 與成功率結果；500 人先前未通過的結果仍保留，不能線性外推。

## 與 500 人結果比較

100 人測試只降低產生端用戶數，沒有縮短 10 分鐘、移除上傳／草稿或更改模型 500ms。先前 500 人第二輪瀏覽器 ASR E2E P90 2.447s、翻譯 E2E P90 4.150s，並有 61,768／150,000 段丟棄，因此 500 人未通過。兩輪的應用程式版本不同，不能把差異全歸因於人數；詳細失敗、修正版短測及限制見 [500 人報告](PERFORMANCE_500_2026-10-21.zh-TW.md)。

待處理項目包括：500 人完整重測、儲存／清理與 event-loop 長尾、MinIO 記憶體餘裕、真實 Sentinel 切主，以及實際 vLLM／外部網路／更多真實瀏覽器的驗證。
